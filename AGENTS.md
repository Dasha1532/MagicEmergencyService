# Правила проекта «Магическая аварийная служба»

## Язык общения

- Всегда общаться с пользователем на русском языке.
- Переходить на другой язык только по прямой просьбе пользователя.

## Назначение проекта

- Это самостоятельная 2D-игра на Godot 4.x и GDScript.
- Рабочее название: «Магическая аварийная служба».
- Проект не смешивать с Echoes of the Creator: Infinite Cycles и Roblox CafeLivingStories.

## Репозиторий и Git

- GitHub-репозиторий проекта: https://github.com/Dasha1532/MagicEmergencyService
- Основная ветка: main.
- В Git хранить исходники, сцены, настройки, документацию и разрешённые ресурсы.
- Не добавлять .godot/, экспортированные сборки и временные файлы.
- Файлы .uid, созданные Godot рядом с исходниками, сохранять в Git.
- Не создавать коммит или отправку в GitHub без явного подтверждения пользователя.

## Начало каждой задачи

- Сформировать краткую цель, ограничения и критерий готовности.
- Прочитать этот файл и относящуюся к задаче документацию.
- Проверить git status и относящийся к задаче diff.
- Не считать непроверенные изменения рабочей стабильной версией.

## Способ работы с Godot

- По умолчанию изменять проект через .gd, .tscn, .tres и project.godot.
- Не редактировать содержимое .godot/.
- Предпочитать отдельные сцены для повторно используемых объектов.
- Отделять данные, игровую логику и визуальное представление.
- Для проверки использовать headless-режим Godot, если он доступен.

## Архитектура

- Механики объектов, инструментов, реакций, жильцов, заявок, экономики и репутации делать data-driven.
- Не зашивать уникальные цепочки последствий в отдельные заявки.
- Сохранять версию формата сохранений и предусматривать безопасную миграцию.
- Внутренние теги и технические параметры не показывать игроку вне debug-режима.

## Визуал и ресурсы

- Использовать 2D cutaway/dollhouse-подачу с тёплой реалистично-фэнтезийной атмосферой.
- Временные ассеты должны быть аккуратными и пригодными для прототипа.
- Перед добавлением внешних ресурсов проверять лицензию и сохранять сведения об авторстве.

## Безопасные изменения

- За одну итерацию менять одну механику или одну причину ошибки.
- Сначала фиксировать наблюдаемое поведение, затем вносить минимальный патч.
- Не переписывать большие файлы целиком без необходимости.
- При регрессии остановиться и вернуть только последнее изменение.
